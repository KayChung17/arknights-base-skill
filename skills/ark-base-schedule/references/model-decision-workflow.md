# 模型决策工作流

## 角色分工

大模型负责确定问题，脚本负责求解已经结构化的问题。

大模型需要确定：

- 用户对龙门币、合成玉、经验、操作次数和心情风险的相对权重。
- 设施等级、产品分配和操作节点。
- 哪些网络资料可以转化为已验证技能证据。
- 哪些限制属于硬约束，哪些属于目标函数。

混合求解器负责：

- 枚举单房间合法组合。
- 同时选择所有房间和区间。
- 排除同一时间重复进驻。
- 处理心情与宿舍闭环、资源平衡和仓库容量。
- 输出多个候选及 MILP gap。
- 复算全局联动和经济指标。

## 攻略的位置

当前攻略需要进入候选比较集，并提供机制核对和收益基线。攻略方案不限制：

- 控制中枢选择。
- 贸易站和制造站组合。
- 房间级换班周期。
- 无人机分配。
- 用户目标权重。

当求解器方案偏离攻略时，模型说明偏离原因、收益、风险和数据依据。

## 迭代顺序

1. 使用中等候选池快速求解。
2. 检查 `truncated_rooms`、仓库损失、资源负平衡和心情警告。
3. 对关键房间扩大 `operator_pool_size` 与 `top_k`。
4. 调整目标权重或硬约束。
5. 重新求解并比较。
6. 将当前攻略方案作为同口径候选复算。
7. 选择符合用户偏好的候选。

## 停止条件

出现以下情况时停止升级为 final：

- 关键生产干员技能没有验证数据。
- MILP 无可行解且没有解释冲突约束。
- 仓库、心情或碎片平衡存在未处理警告。
- 用户的实际设施等级或操作时间仍不明确。
- 组合库发生关键截断且尚未扩大搜索。
