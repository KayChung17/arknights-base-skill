# 项目配置说明

配置采用 JSON，Schema 位于：

```text
skills/ark-base-schedule/schemas/project-config.schema.json
```

## 顶层字段

| 字段 | 含义 |
|---|---|
| `schema_version` | 当前固定为 1 |
| `project_name` | 报告显示名称 |
| `mode` | `layout_search`、`upgrade_search` 或 `fixed_schedule` |
| `roster` | TSV、CSV 或 XLSX 路径 |
| `output_dir` | 默认输出目录 |
| `layout` | 固定排班模式使用，例如 `342` |
| `operator_overrides` | 本次运行的干员精英化、等级、招募或心情覆盖；不改写原 roster |

场景覆盖示例：

```json
"operator_overrides": {
  "八幡海铃": {"elite": 2, "level": 70}
}
```

## objective

| 字段 | 含义 |
|---|---|
| `online_times` | 每天可操作节点；不等同于强制换班 |
| `minimum_net_lmd_per_day` | 每日龙门币净变化下限，可为负数 |
| `minimum_originium_shard_balance` | 源石碎片日净变化下限；省略时默认 0 |
| `minimum_pure_gold_balance` | 赤金日净变化下限；省略时默认 0 |
| `max_orundum_trading_posts` | 外层搜索允许的合成玉贸易站上限 |
| `max_shard_factories` | 外层搜索允许的碎片制造站上限 |
| `minimum_battle_record_factories` | 外层搜索至少保留的经验书制造站数量；默认为 0 |

长期重复日默认维持源石碎片和赤金收支：两项日净变化均不得为负；主目标收益相同时，优先总偏差更接近 0 的候选。“库存充足”或“不考虑库存日净变化”不会放宽该规则。主动消耗库存需要显式填写负下限，并在项目说明中记录可持续期限。

## base_state

`drone_capacity` 来自基建区域清理进度，发电站数量和等级不会改变该上限。`initial_drone_stock` 是第一次执行时的库存；重复日模式会要求次日回到同一状态。

`right_side_levels` 用于电力预算。会客室、办公室、训练室和加工站各只有一间，且升级后不可降级；这四项等级必须来自用户当前基建状态。配置还需写入 `right_side_levels_confirmed: true`，使严格预检确认这些数字是等级。

宿舍等级同时影响耗电和基础心情恢复。布局搜索按各候选宿舍等级的满氛围上限计算基础恢复，随后在每个上线区间分配最多 5 个床位，并验证逐干员重复日心情闭环。宿管技能未结构化时按 0 处理。

攻略图片可用于提供同组、大组和候选 bundle 提示。图片颜色与效率百分比不会直接覆盖本地干员数据；动态换班只允许发生在 `online_times` 中的节点，当前三次上线配置不会计算节点外自动换班收益。

右满配置与固定耗电是：

```json
"base_state": {
  "right_side_levels": {
    "reception_room": 3,
    "office": 3,
    "training_room": 3,
    "workshop": 3
  },
  "right_side_levels_confirmed": true
}
```

会客室 60 + 办公室 60 + 训练室 60 + 加工站 10 = 190 电力。外层布局搜索把这 190 作为固定耗电；固定排班在预检阶段直接拒绝缺电配置。

## profiles

### representative

使用仓库维护的常见代表配置，速度快。

### level_grid

枚举选定布局的贸易站和制造站等级多重集，按电力过滤，再按 `max_profiles` 截断后求解。结果会记录：

- 可行 profile 总数
- 实际求解数量
- 是否发生截断

### 自定义文件

`profiles.file` 可指向 `examples/profiles/自定义布局等级.json` 格式的文件。

## search

`top_k` 和 `operator_pool_size` 越大，单房间候选越完整，求解时间也越长。发布结论前应对排名第一和接近的备选扩大候选库复算。

`lmd_proxy_floor_slack` 只放宽 MILP 代理模型；最终模拟仍按实际龙门币下限拒绝候选。常规使用建议保持 0。

## upgrades

`marginal_limit` 表示对前 N 项培养执行“定向方案中移除该升级后重新求解”。该方法能够识别协同技能和不可逆技能，但计算量约增加 N 次完整布局搜索。

## verification

`relevant_unmodeled_skill_policy` 控制本次设施与产品范围内未结构化技能的门禁：

- `warn`：继续求解，在审计、验证和 `unmodeled-relevant-skills.json` 中记录风险。
- `block`：存在带数值或动态公式特征的未结构化技能时，在求解前进入 `execution_blocked`。

发布结论建议使用：

```json
"verification": {
  "relevant_unmodeled_skill_policy": "block",
  "strict_warnings": true
}
```

`require_all_unlocked_skills_structured` 会检查全部已解锁技能，范围更严格；日常项目通常使用相关设施与产品门禁。

## 输出文件

完整运行将 `schedule.json` 作为正式排班表。它兼容 `skills/ark-base-schedule/assets/template.json`，每个上线区间对应一个 `plans` 条目，`scheduleType` 记录贸易站、制造站、发电站和宿舍数量。

`result.json` 保存求解和逐区间模拟详情；`report.md` 用于阅读；`run-manifest.json` 和 `verification.json` 用于发布验证。
