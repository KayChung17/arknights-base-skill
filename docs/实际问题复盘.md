# 实际问题复盘与 1.0.0 改进

本仓库的 1.0.0 不是对早期脚本的界面包装。以下改动来自多轮真实排班问题中暴露出的缺陷，并已转化为可复现配置、硬约束、审计项和回归测试。

## 模板只能作为基线

早期流程从攻略模板替换缺失干员，搜索范围局限在模板附近。跨房间联动、新干员体系、不同班次长度和仓库扩容组合容易被漏掉。

当前流程将攻略保存为基线候选。外层搜索布局、建筑等级和产品分配；内层枚举房间组合并由 MILP 处理跨房间冲突。报告同时列出模板差异和候选库截断状态。

## 建筑状态必须来自用户配置

早期方案曾把攻略中的贸易 331、制造 3322 和一级宿舍直接套入用户账号，导致“满级建筑”与电力预算混淆。

当前配置分别记录贸易站、制造站、发电站、宿舍和右侧设施等级。`representative` 只是快速候选集，`level_grid` 和自定义 profile 可以搜索不同等级组合。电力不可行的配置在求解前拒绝。

## 数据覆盖不足会制造假性无解

只有少量干员的结构化技能时，求解器会正确地判定候选库无法填满所有房间，但这个结果不代表用户账号没有可行排班。

当前项目提供独立覆盖报告，区分：

- 干员名称是否收录；
- 当前练度下解锁了多少技能；
- 技能是否已有直接数值；
- 复杂技能是否有机制标签；
- 仅保留描述、尚未结构化的技能数量。

报告与审计必须把“数据缺失”与“数学不可行”分开表述。

## 验证必须复用公开运行链路

早期曾出现验证摘要显示可行，而使用 README 命令重新运行却无解。根因是验证参数、候选库和公开入口不一致。

当前发布流程通过同一个项目配置入口执行端到端自检，并将配置副本、输入哈希、运行环境和求解范围写入结果。发布包构建会再次运行完整校验。

## 无人机需要形成完整库存流

早期只记录发电站恢复能力，没有决定无人机在何时投入哪个设施；也曾混淆持有上限、供电和恢复速度。

当前模型分离：

- 持有上限；
- 发电站供电；
- 已进驻发电站与干员技能提供的恢复；
- 操作节点上的整数分配；
- 容量溢出；
- 重复日库存闭环；
- 加速制造或订单产生的资源成本。

审计器会检查库存非负、容量上限以及重复日恢复、使用和浪费是否闭合。

## 代理目标不能冒充最终产出最优

部分特殊订单、订单随机性、仓库封顶和全局联动更适合在求解后模拟。代理 MILP 的最优解不必等于最终模拟产出的全局最优解。

当前输出分别记录 profile 截断、房间组合截断、MILP gap、时间限制 incumbent 和最终模拟状态。正常结果只称为“当前搜索设置中的最高分候选”。

## 培养不是单调变量

孑、冬时等干员升级后会改变技能形态，升练度不保证基建收益增加；部分升级不可逆。只计算“全部升满”会给出错误建议。

当前培养搜索先求技能上限，再提取候选实际使用的更高技能，并支持留一法边际复算。报告必须标记非单调和不可逆状态；没有培养成本数据时，只评价基建产出，不声称投资回收最优。

## 用户数据与发布仓库必须隔离

真实 roster、库存、心情和求解结果属于个人数据，不应进入公共仓库。

当前 `.gitignore` 排除常见 roster 和输出目录；公共仓库移除真实账号原始导出，并从结构化快照删除来源账号练度、拥有状态和原始行号。发布脚本只打包版本化代码、文档、合成示例和脱敏数据快照。

## 仍需继续完善

1. 将日内产品切换纳入外层决策，而不只使用全天固定产品。
2. 将宿舍床位、精确氛围、菲亚梅塔和恢复链纳入全局模型。
3. 扩充全游戏技能数据，并为每条结构化机制维护来源和版本。
4. 对普通订单随机性提供期望、保守分位数和蒙特卡洛三种口径。
5. 增加培养资源成本和回收周期模型，使“产出最大”与“投资划算”可以分别求解。
