# 技能与机制数据维护

## 原则

- 原始描述必须保留。
- 只结构化能够确定的数值。
- 每条数据记录来源、日期、版本和适用范围。
- α/β 或同组技能只选择当前最高已解锁版本。
- 覆盖同站效率、订单数、仓库转化等非线性技能必须使用机制标签和组合测试。
- 来源不明确时保留为待核验，不给出猜测数值。

## 导入全量干员技能表

```bash
python skills/update-ark-skills/scripts/import_owned_skill_table.py \
  --input skills_parsed.txt \
  --existing skills/ark-base-schedule/assets/operator-skills.json \
  --output skills/ark-base-schedule/assets/operator-skills.json \
  --data-version YYYY-MM-DD-source \
  --warnings-output import-warnings.txt
```

## 发布前检查

```bash
python skills/ark-base-schedule/scripts/validate_data.py
bash scripts/validate-all.sh
```

`skills_parsed.txt` 是全局技能来源，`operator-skills.json` 是合并复杂机制覆盖层后的运行时数据。真实账号的拥有状态和练度只存放在用户本地 roster；导入器回归使用 `tests/fixtures/owned-skill-table.sample.txt` 的最小合成样例。

## 动态技能结构化

直接百分比继续使用 `base_bonus_pct`，复杂联动使用 `tags`，依赖配置数值的通用公式使用 `mechanism`。例如按无人机上限每 10 点增加 1%、最多 25%：

```json
{
  "model_status": "structured",
  "mechanism": {
    "type": "step_bonus",
    "input": "drone_capacity",
    "step": 10,
    "bonus_pct_per_step": 1,
    "cap_pct": 25
  }
}
```

`model_status` 可取 `structured`、`verified_zero`、`conservative_zero`、`description_only`、`unsupported`。真实零收益使用 `verified_zero`；明确忽略只会改善可行性的收益使用 `conservative_zero`；仍待实现的文字机制使用 `description_only` 或 `unsupported`。

## 技能槽与叠加规则

`variant_group` 是技能槽标识。同一组的 α/β/γ 或改名升级只启用当前练度下的最高阶段；不同组表示可同时生效的独立技能。名称完全变化的升级关系需要加入 `KNOWN_VARIANT_GROUPS`，数据校验会检查 α/β/γ 后缀技能是否误分到多个组。

生产相关的“同种效果取最高”使用 `effects`：

```json
{
  "effect_key": "global_trading_order_efficiency_pct",
  "stacking": "max",
  "value_pct": 7
}
```

动态数值可以在 effect 内使用 `mechanism`。结算器按 `effect_key` 归组，再执行 `add`、`max`、`replace`、`multiply` 或 `exclusive`。

“与部分技能有特殊叠加规则”使用 `special_rules`。规则必须记录类型、排斥技能、优先级及必要的群组或设施参数。生产技能出现上述文案但缺少结构化规则时，数据校验和相关技能门禁都会阻断发布。

2.0 的机制来源与适用范围见 `references/mechanic-sources.md`。更新阵营名单、解锁条件或特殊叠加时，同步更新 `assets/data-version.json` 的版本、日期和来源。
